# A link stores what it joins

Four things share a transaction's `linkID`: the two halves of a Transfer (ADR-0002), the parts of a Split (ADR-0007), a Loan or Debt with its payments and what it writes off beside them (ADR-0003), and an Expense with its paybacks into other wallets (ADR-0010). Until now nothing said which, so every rule worked it out again from the category, `hasPaybacksElsewhere` and, to tell a part of a Split from a Debt write-off, a store fetch inside a computed property (`sharesLinkWithLoanOrDebt`). Each copy excluded the kinds it did not want a little differently, a write-off could be taken for a Split part, and the fetch grew single-caller variants (`isSplitPart(loanOrDebtLinks:)`, `editFlow(isSplitPart:)` and the rest) that a screen had to call in a fixed order.

**Each transaction on a link stores the link's kind** (`Transaction.linkKind`, stored as `linkKindRaw`: `transfer`, `split`, `loanOrDebt` or `payback`), beside `linkID`. Both are set only through `Transaction.link(_:as:)`, `join(_:as:)` and `leaveLink()`, which the one rule that makes each kind of link calls: `Transfer.create`, `Transaction.split` and `undoSplit`, `LoanOrDebt.addLinked` and `linkPayment`, `recordPaybackElsewhere`, and the import. Every role check reads the stored kind (`isSplitPart`, `isDebtWriteOff`, `editFlow`, `canBeSplit`, `checkPayback`), so none of them touches the store. A link is a shared value rather than a record of its own, so the kind is copied onto each member; a link always has one kind, because the rules never put a linked transaction onto a link of another kind.

A store from before is brought up to date once, when it opens (`Transaction.migrateLinkKinds(in:)`, run beside `Person.migrateWithNames`): each link without a kind gets the one its transactions say (`LinkKind(of:)`): a transfer half makes it a Transfer, a Loan, Debt or payment a Loan or Debt's, a payback or an Expense marked paid back a payback's, and the rest a Split, as they were taken to be before. A Grosh export numbers its links without saying what they join, so the import works the kind out the same way.

**`hasPaybacksElsewhere` is now cleared** once the Expense's last payback is removed for good, and the Expense leaves its link with it, so it can be split and change wallet again. This supersedes ADR-0010's "set when its first payback is recorded and never cleared". A payback waiting in Recently Deleted still keeps the flag, since restoring it needs the Expense where it was. The migration clears a flag already stale.

Consequence: a Debt write-off whose Loan was removed for good stays a write-off, rather than turning into a part of a Split as the old store lookup made it.
